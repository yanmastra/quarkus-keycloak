## [4.3.0] / quarkus-media-file-manager 1.0.2 — 2026-09-27

### quarkus-redis-cache (new)
- Stores the key/value cache (login sessions, cookie tokens) in Redis instead of local files, using the Quarkus Redis client
  - Add the extension to a service and configure `quarkus.redis.hosts`; no code changes are needed
  - One Redis hash per cache (`<prefix>:<cacheName>`), so a read/write touches one field instead of rewriting a file
  - Values are AES-GCM encrypted; the key is generated by the first instance and kept in Redis, so all instances share it
  - `cache.redis.enabled` (default `true`), `cache.redis.key-prefix` (default `kvcache`), `cache.redis.encrypt` (default `true`)
- Existing local cache files are moved into Redis automatically at start-up (files are kept as `*.migrated` backups)
- Moving back: set `cache.redis.enabled=false` and start once with the extension still present; Redis is drained into local files, then remove the extension
- Services that do not use it get no Redis dependency
- Integration tests default to Quarkus Dev Services (no setup needed); a `manual` test profile connects them to a real
  Redis instead (e.g. `infra/docker`'s `redis` service): `mvn test -Dquarkus.test.profile=manual -DREDIS_PASSWORD=...`
- Docs expanded (`docs/redis-cache.md`) with a "which thread is this on" checklist for anything that calls the cache
  outside a normal blocking endpoint — service classes, Qute rendering, `ErrorEvent` observers, `HtmlErrorMapper`,
  Vert.x handlers. These extensions are consumed by projects we don't control, so we can't audit or limit how a
  consumer wires the cache; calling a blocking method from the Vert.x event loop fails loudly with a message pointing
  at the `*Async` alternative — it doesn't corrupt data or hang, but nothing in this extension can prevent a consumer
  from hitting it
- See `docs/redis-cache.md`

### quarkus-base
- `KeyValueCacheUtils` can now use another storage: new `KeyValueCacheStore` interface and `KeyValueCacheUtils.registerStore(...)`; the public `saveCache`/`findCache`/`removeCache` methods are unchanged
- Added non-blocking `saveCacheAsync`/`findCacheAsync`/`removeCacheAsync` (`Uni`); results are delivered back on the caller's Vert.x context
- Generic, idempotent migration between stores (`KeyValueCacheMigrator`): never overwrites newer data, resumes after a failure, guarded by a lock so several instances can start together
- The local-file logic moved into `FileKeyValueCacheStore` with the same file format; existing cache files keep working
- Fixed the default cache directory: without `cache_directory`/`CACHE_DIRECTORY` it was resolved with `System.getenv("user.dir")` (always `null`), so files went to `./null/.cache_v2`. It is now `./.cache_v2`. **Upgrade note:** services that never set `cache_directory` will not see their old sessions (users log in again); set `cache_directory=./null` to keep using the old location
- Saving a blank value removes the key (as before), but a key that was removed now reads as `null` instead of `""`
- Added unit tests (JUnit 5); surefire updated to 3.5.3

### quarkus-authentication
- Cookie session lookups in `AuthenticationMechanism` no longer block the event loop (required for Redis, and an improvement for local files)
- If the cache cannot be reached, the cookie is treated as absent: the request falls back to the `Authorization` header and is rejected with 401 only if that is missing too
- Added non-blocking `CookieSessionUtils.getSessionValueAsync`/`putSessionToCacheAsync`
- Added `AuthenticationService.createAccessTokenAsync` (payload and refresh-token variants), `checkSessionAsync`, `getUserIdAsync`, `removeSessionAsync`, `logoutAsync`. Use these from reactive endpoints (`Uni`/`@NonBlocking`); the blocking methods keep working on worker threads
- `createAccessToken` now signs the tokens before it writes the session to the cache

### quarkus-authorization, quarkus-microservices-common, quarkus-error-mail-notification
- No functional changes — version aligned with quarkus-base

### quarkus-media-file-manager
- No functional changes — dependency on quarkus-base bumped to 4.3.0

### infra
- Added a `redis` service to `infra/docker/docker-compose.yml` (password via `REDIS_PASSWORD`, port via `REDIS_EXTERNAL_PORT`)

## [4.1.4] — 2026-05-19

### Fixed

#### `quarkus-base`
- **`KeyValueCacheUtils` — concurrent request safety** (`KeyValueCacheUtils.java`)
  - Added 32-stripe `ReentrantReadWriteLock` array to prevent `java.nio.channels.OverlappingFileLockException`
    when multiple threads in the same JVM access the same session cache file concurrently.
  - Root cause: `java.nio.channels.FileChannel.lock()` is designed for inter-process locking only.
    Within the same JVM, two threads calling `lock()` on the same file (even with shared read mode)
    throws `OverlappingFileLockException` immediately — it does not queue or wait.
  - **`findCache`** now acquires a JVM-level read lock (`ReadWriteLock.readLock()`) before calling
    the shared `FileChannel.lock()`, allowing multiple concurrent reads without conflict.
  - **`saveCache`** / **`removeCache`** now acquire a JVM-level write lock (`ReadWriteLock.writeLock()`),
    blocking all readers and other writers within the JVM before the exclusive `FileChannel.lock()`.
  - Striped design: 32 fixed lock objects (~1.6 KB total memory) ensure different sessions
    rarely contend; same session always maps to the same stripe and serializes safely.
  - `FileChannel.lock()` calls are preserved for cross-process (multi-instance) safety.

### Changed

- All extensions bumped from **4.1.3 → 4.1.4** to consume the `quarkus-base` fix:
  - `quarkus-authentication`
  - `quarkus-authorization`
  - `quarkus-microservices-common`
  - `media-file-manager`
- `quarkus-error-mail-notification` bumped from **4.1.2 → 4.1.4**.

### Migration

Update the version property in your consumer project's `pom.xml`:

```xml
<properties>
    <quarkus-keycloak.version>4.1.4</quarkus-keycloak.version>
</properties>
```

No API changes — this is a drop-in replacement.
